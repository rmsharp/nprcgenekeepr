# Docs staleness audit, slice 2: the 50 `shiny_app_use/` screenshots (2026-09-30, S821)

Read-only audit. Nothing in the repo was changed except this report and the records; the committed images were
overwritten by the capture scripts during measurement and restored with `git checkout` (verified: no tracked diff).

## Audit summary

- **Scope:** all 50 PNGs in `vignettes/articles/shiny_app_use/`.
- **Criterion:** does the committed image still show what the app shows today? Measured by running the project's own
  capture scripts against the current app and comparing pixels (`png` package; a pixel counts as different when any
  channel differs by more than 0.1). Counted, not recalled.
- **Method:** `colony-manager-guide-screenshots.R` run twice, `pedigree-diagram-screenshots.R` once; originals saved
  first. Pairs that looked different were viewed. Run 1 and run 2 agree on 43 of 50 images (the 7 that differ are 4
  `pb_*` and 3 `ss_*` captures, so those are not stable between runs).
- **Coverage:** 38 of 50 regenerated and compared. 12 have no generator (9 `marker_genetics_*`, 3 `ss_*` CSV views);
  judged only by module history (finding 3).
- **Findings:** 0 critical, 2 moderate, 3 minor.

## Findings

### 1. Moderate: about two thirds of the committed screenshots no longer match the app
- **Location:** `vignettes/articles/shiny_app_use/` (groups above); used by `vignettes/articles/colony-manager-guide.qmd`.
- **Evidence:** 31 of the 38 regenerable images differ in size or content from a fresh capture; 23 of them
  (Pedigree Browser family, Home, Input, Summary Statistics) change size, which cannot be anti-aliasing.
  Last committed 2026-08-10 for most; the app has since gained tabs and longer help text.
- **Impact:** the colony-manager guide shows a navbar and panels a user will not see.
- **Recommendation:** regenerate in a later session, after finding 2 is understood. Note the Home page prints a
  version date, so the shot will date again; consider whether that line should be cropped or removed from the app's
  landing text.

### 2. Moderate: the capture script's tail fails the same way every time
- **Location:** `vignettes/articles/colony-manager-guide-screenshots.R` from the seeded 6-group Breeding Groups
  step onward (about lines 480-650).
- **Evidence:** both full runs reported 76/81 steps succeeded with the same 5 failures: select group 6, Potential
  Parents results, Marker Genetics navigation, the Mate Pair exclude-list textarea, Mate Pair completion. After the
  6-group formation, every `set_inputs(mainNavbar = ...)` reports "Server did not update any output values within 4
  seconds" and `wait_for_idle` times out. The script's own comment (line 87-92) knows Shiny stays busy after group
  formation.
- **Impact:** 4 images cannot be regenerated by the script as it stands, and the 2 images before them are unreliable.
  Whether the app is genuinely hung after formation or the script's waits are too short is **not determined**;
  I did not diagnose it (separate deliverable).
- **Recommendation:** its own session using the `diagnose` skill: reproduce by hand in the running app first.

### 3. Minor: 12 images have no generator
- **Evidence:** the 9 `marker_genetics_*` and 3 `ss_*` CSV screenshots are not written by any script under
  `vignettes/articles/` or `data-raw/`. Commits to `R/modMarkerGenetics.R` since each image was last updated: 12, 11,
  10, 10, 8, 6, 7, 7 (the 8 older images) and 0 (`marker_genetics_mhc_haplotype.png`, 2026-09-18). Commit counts do
  not prove a visible change, so these are **unverified**, not stale.
- **Recommendation:** check by hand against the running tab, or add them to a capture script.

### 4. Minor: `pb_unknown_displayed.png` is unreferenced
- **Evidence:** generated by `colony-manager-guide-screenshots.R:242`, but no `.qmd`, `.Rmd`, manual component,
  `ui_guidance` page or the README mentions it.
- **Recommendation:** delete it and its capture call, or use it.

### 5. Minor: the GVA ranking screenshots depend on tie order
- **Evidence:** in `gva_first_high_value.png` the top 10 rows are animals `0J5JEH`, `4BWI4P`, ... in the committed
  image and `0SPRLB`, `2WMICB`, ... in a fresh capture, all with the same mean kinship (0.0001353...). Run 1 and run 2
  produced identical images, so this run is deterministic; the committed image came from a different state (code or
  seed) and ties are broken arbitrarily.
- **Recommendation:** when regenerating, check the article prose does not name specific animals from these tables.

## Structural observations
- Most staleness is one cause repeating: a longer help text or an extra control shifts a whole panel, so every image
  of that module changes together. Regenerating by module is the natural unit.
- The capture scripts are good: they replaced the images in place and make the comparison cheap. The weak point is the
  tail of the colony script (finding 2) and the 12 images outside any script (finding 3).

## Comparison with slice 1
Slice 1 found 1 of 8 kinship2 images stale; here 31 of 38 regenerable images differ. Different image families, so no
trend; the user-guide screenshots are the weaker set.

## Recommendations
1. Diagnose the capture-script tail failure (finding 2) before any regeneration.
2. Then regenerate by module, looking at each pair first (Input and Summary Statistics causes are still unviewed).
3. Decide delete or use for `pb_unknown_displayed.png`; hand-check or script the 12 ungenerated images.
4. Slice 3: the prose claims in the articles, then the rest of the user-facing and internal scope (see `BACKLOG.md`).
